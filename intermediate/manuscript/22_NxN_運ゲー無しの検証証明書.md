# 第22章補稿：10×10でも「確実な一手」を証明書で確かめる

> **編集用補稿・配布PDF未収録。** 以下の生成器と検証器はPython参照実装です。Bendの10×10完成ゲーム、GUI、全称証明ではありません。第22章の既存Bend例 `14_local_inference.bend` を理解した後に読む補助資料です。

## なぜ「生成できた」だけでは足りないのでしょうか

10×10の盤面に地雷を10個置くと、配置は非常に多くなります。初手が安全でも、その後に数字だけから次の安全マスを選べるとは限りません。そこで、盤面を作る側と推理する側を分けます。**推理する側には、まだ開いていないマスの地雷位置を渡しません。**

4×4の小例では全盤面を列挙できましたが、10×10では公開数字に隣接する未公開マスだけを制約で結ぶ「フロンティア」を利用します。離れた未公開マスについても総地雷数の制約を使います。Python参照実装 `intermediate/solutions/nxn_frontier_solver.py` は探索上限に達した場合、安全を主張しません。

## 実際に生成し、結果を確かめましょう

リポジトリのルートで、次を実行します。

```sh
PYTHONPATH=intermediate/solutions python3 - <<'PY'
from nxn_noguess_generator import generate_no_guess_frontier, verify_certificate
cert = generate_no_guess_frontier(10, 10, 10, 0, seed=20261023)
print(sorted(cert.mines))
print(cert.clicks)
print(verify_certificate(cert))
PY
```

検証済みのPython参照環境では、次のように出力します。

```text
[4, 29, 34, 36, 37, 49, 50, 56, 72, 77]
(0, 14, 5, 6, 24, 35, 38, 39, 46, 47, 48, 57, 67)
True
```

初手は左上の添字0です。初手とその近傍には地雷を置かないため、最初の公開で0領域が連鎖して開きます。その後は公開された数字と総地雷数から**必ず安全だと分かった**マスだけを順に開きます。0領域の連鎖公開により、クリック回数は安全マス90個より少なくなります。

`verify_certificate` は、公開数字から各クリックの安全性を再計算し、最後に90個の安全マスがすべて公開されたことを検査します。数字を使う推論器は `Visible` のみを受け取り、真の地雷配置はクリック結果を作るゲーム側だけが保持します。

## どこまで保証したのでしょうか

この `True` は、**指定した10×10・10地雷の配置、初手0、表示されたクリック列について有限の再生検査が成功した**ことを意味します。任意の盤面や初手について推測不要であるという主張ではありません。また、採用されなかった盤面にも別の安全なクリック順があるかもしれません。

探索上限に達したとき、公開数字が矛盾するとき、安全な次の手が見つからないときは候補を採用しません。`GenerationFailed` を捕まえて未検証の盤面を返してはいけません。テストでは途中のクリックを削った証明書、地雷を開く証明書、範囲外の番号、探索上限の不足を拒否します。

**Bendへの移植は未完了です。** 今回のPython実装と6件のテストは、将来BendのN×Nゲームエンジンと公開情報ソルバーを接続するときの比較対象です。第21章の既存4×4 GUIを10×10対応済みとは扱いません。

## 10×10の一手ごとの公開状態を記録してみましょう（Bend移植用の比較表）

10×10の運ゲー無し候補を生成できても、ゲーム本体の0連鎖や数字表示が同じように動くとは限りません。そこで、クリックごとの**公開済みマス・数字・勝敗状態**を比較できる形にしておきます。隠された地雷配置は盤面を再生するためだけに使い、公開状態の行には含めません。

リポジトリのルートで次を実行してみましょう。これはPython参照実装の検査であり、Bendの実行結果ではありません。

```sh
PYTHONPATH=intermediate/solutions python3 - <<'PY'
from nxn_replay_vectors import replay_vectors
mines = frozenset({4, 29, 34, 36, 37, 49, 50, 56, 72, 77})
clicks = (0, 14, 5, 6, 24, 35, 38, 39, 46, 47, 48, 57, 67)
frames = replay_vectors(10, mines, clicks)
for frame in (frames[0], frames[-1]):
    print(frame.click, len(frame.opened), frame.phase)
    print(','.join(f'{word:08x}' for word in frame.opened_words))
PY
```

```text
0 66 Playing
c0f03c0f,fcf83f03,ffffdef7,0000000f
67 90 Won
dfffffef,fef9ffcb,ffffdeff,0000000f
```

最初のクリック0で66マスが開き、最後のクリック67で安全な90マスがすべて開きます。`opened_words` は公開済みの添字を32ビットずつ格納した値です。**地雷ビット列ではありません。** たとえば添字32の公開状態は2番目の語の最下位ビットで表します。100マスの盤面には4語が必要で、最後の語の上位28ビットは使いません。

`render_replay(frames)` は各手の番号、公開数、状態、公開ビット列、新たに公開された `添字:数字` を一行ずつ出力します。これらの行を将来のBend版N×Nゲームの出力と照合すれば、0連鎖の停止位置、数字の境界、勝利への遷移を一手ずつ調べられます。既存の `nxn_board_oracle.py` と、別のキュー探索による参照計算でも13手すべてを比較します。

ただし、**公開状態の一致は「推測不要」の証明ではありません。** 各手の安全性は前節の `audit_certificate` が公開数字だけを使って独立に検査します。Bend側のN×N状態遷移・GUI・保存・一般の法則証明は未実装または未検収です。
