## 100マスでも、配列の容量は100とは限りません

4×4の盤面だけなら、16マスの添字を手で確認できます。しかし、
10×10に広げると、クリック位置の検査や勝利判定で盤面外を
誤って数える危険があります。まず座標だけを独立した関数で扱いましょう。

`intermediate/minesweeper/nxn_geometry.bend` の `main` は
`index(10, 5, 5)` を計算します。

```bend
def index(+n: U32, +x: U32, +y: U32) -> U32:
  (y * n + x : U32)

def main() -> U32:
  index(10, 5, 5)
```

`bend intermediate/minesweeper/nxn_geometry.bend` の出力は `55` です。
左上を(0,0)、xを列、yを行とし、行優先で `i=y*N+x` を計算します。
この `index` は有効な座標を受け取ることが前提です。外部のクリックには
`checked_index` を使い、無効なら `None` にします。

Bendの `Array.new` の深さ `d` は `2^d` 個の格納領域を表します。
10×10では `d=7` なので物理的に128スロットありますが、
100..127はマスではありません。盤外クリックも勝利判定も、
必ず `0<=i<N*N` を確認してから処理しましょう。

## 座標の正しさとゲーム全体の正しさは別です

座標を正しく変換できても、地雷を開いてしまう0連鎖や、
旗だけで勝利する誤実装を防げるとは限りません。
そこで次の状態不変条件を独立に確認します。地雷数の保存、
開いたマスが安全であること、数字が近傍地雷数と一致すること、
公開済みマスが閉じないこと、勝敗確定後に操作できないことです。

`python3 -m unittest discover -s intermediate/tests -p 'test_nxn_game_invariants.py' -v`
で、2×2の全60初手と10×10の固定乱数6,000操作を検査できます。
ただしこれは**Python参照モデルの有限テスト**です。
BendのN×Nゲームエンジンが完成したことも、すべての入力について
`law` が証明されたことも意味しません。

## 地雷の内部表現を32ビット語へ分ける（参照モデル、PDF未統合）

N=10では100マスの地雷を単一のU32に格納できません。そこで
`intermediate/solutions/nxn_word_storage.py` は地雷集合を
`ceil(N*N/32)` 個の32ビット語へ分割する**独立Python参照モデル**です。
Bend版の盤面状態を実装する際の入力契約・期待値を先に固定します。

```python
from nxn_word_storage import pack, has, set_cell, unpack
words = pack(10, {31, 32, 99})
print(words)                                    # (2147483648, 1, 0, 8)
print(has(10, words, 32))                       # True
print(sorted(unpack(10, set_cell(10, words, 32, False))))  # [31, 99]
```

32番は**次の語の0ビット目**です。99番は4語目の3ビット目に対応します。
100〜127番は語の末尾に存在する28個の余剰ビットであり、地雷にできません。
これは`Array.new`で確保される**余剰スロット**とは別の概念です。
N=10の可視状態Arrayは128スロット、地雷集合はU32の4語（128ビット）
という二種類の容量を区別します。

`validate`は語数・U32範囲・末尾の余剰ビットを検査し、
`set_cell`は元の語列を変更せず新しい語列を返します。
`has`は無効添字にFalseを返しますが、不正な格納形式は拒否します。
Pythonの2×2・3×3全配置と、10×10・100×100を含む境界・乱数操作を
`python3 -m unittest discover -s intermediate/tests -p 'test_nxn_word_storage.py' -v`
で検査します。**Bend版のN×N地雷格納は検証ブランチに試作済みですが、型検査・実行照合が未完了でPR #4には未統合**です。ゲーム遷移・GUI・全称証明も未完成です。

演習として、31番と32番をそれぞれ立てた場合に語列のどの位置が
変わるか予想してみましょう。次に100番を設定する操作が拒否される
理由を説明してみましょう。

## 初手の地雷を別の空きマスへ移す（Python参照モデル、PDF未統合）

最初のクリックで地雷を踏んでもゲームを開始できるようにするには、
その地雷をほかの空きマスへ移す方法があります。ただし移動前後で
**地雷数が変わらないこと**と、**クリックしたマスが安全になること**
を同時に守る必要があります。

`intermediate/solutions/nxn_word_storage.py` の
`relocate_first_click(n, words, clicked)` は、最も番号の小さい
空きマスへ地雷を移します。初手がすでに安全なら元の語列をそのまま返します。
地雷で埋まった盤面、範囲外の添字、不正な格納形式は拒否します。

```python
from nxn_word_storage import pack, relocate_first_click, unpack
words = pack(10, {0, 31, 32, 99})
moved = relocate_first_click(10, words, 32)
print(sorted(unpack(10, moved)))  # [0, 1, 31, 99]
```

ここで32番の地雷は1番へ移ります。0番は地雷なので選べず、
1番が最初の空きマスだからです。語をまたぐ地雷移動でも
`set_cell` が元の語列を変更しないため、元の配置を保存できます。

`python3 -m unittest discover -s intermediate/tests -p 'test_nxn_word_first_click.py' -v`
で、2×2・3×3の全4,659初手、10×10・100×100などの境界・乱数例を
独立した集合モデルと照合します。**BendのN×Nゲーム本体の検証ではありません。**

演習として、クリック位置が最初から安全な場合と、盤面が地雷で
埋まっている場合の動作を確かめてみましょう。

## Bendで32ビット語を読み書きする（本編PDFへの統合前）

Python参照モデルで仕様を決めたので、今度はBendの
`intermediate/minesweeper/nxn_mine_words.bend` に同じ格納層を実装します。
10×10の100マスそれぞれの地雷の有無を、4個の `U32` 語で保持します。
添字 `i` に対して語番号は `i/32`、ビット位置は `i%32` です。

```bend
def bit(+index: U32) -> U32:
  U32.shln(1, U32.to_nat(U32.mod(index, 32)))

def update_word(old: U32, index: U32, value: Bool) -> U32:
  match value:
    case True{}:
      U32.or(old, bit(index))
    case False{}:
      U32.and(old, U32.not(bit(index)))
```

`set_checked` は有効な添字だけを書き換え、`has` は範囲外なら
`False{}` を返します。無効なサイズは `new_checked` が `None{}` にします。

ここではPython参照モデルとの**失敗時のAPI契約の違い**にも注意しましょう。
Pythonの `set_cell` は100番のような無効添字を例外で拒否しますが、
Bendの `set_checked` はその書き込みを無視して元の地雷集合を維持します。
たとえば10×10で0番を地雷にしてから100番を設定・解除しても、
0番は地雷のままです。100〜127番は最後のU32語の余剰ビットであり、
`Array`の容量内にあっても盤面のマスにはなりません。
`bend intermediate/minesweeper/nxn_mine_words.bend` の
`main` は31番と32番に地雷を置いて32番を読むため、予想出力は `1` です。
`python3 intermediate/scripts/test_nxn_mine_words.py` では
N=2/3/4/10/17/100の語数、追加・削除・再追加、31/32番の語境界、
無効添字による書き込みが既存の地雷を壊さないことを、306個の重複なしの
検査式でPython参照モデルと照合する設計です。**検査式の生成とPython側の独立照合は確認済みですが、Bendでの型検査・実行照合は未完了**です。

これは**地雷の内部格納**の教材であり、初手の地雷移動、
近傍数字、0連鎖、勝敗、GUI、運ゲー無し生成を検証したことにはなりません。
内部の地雷語列を公開情報だけを受け取る推論器に渡してはいけません。

**演習：** 31番と32番の地雷を別々に立て、変化する語番号を
予想してみましょう。99番を削除した場合と、無効な100番を
指定した場合の違いも説明してみましょう。
