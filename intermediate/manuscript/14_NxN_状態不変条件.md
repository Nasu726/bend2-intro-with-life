## 100マスでも、配列の容量は100とは限りません

4×4の盤面だけなら、16マスの添字を手で確認できます。しかし、
10×10に広げると、クリック位置の検査や勝利判定で盤面外を
誤って数える危険があります。まず座標だけを独立した関数で扱いましょう。

`intermediate/minesweeper/nxn_geometry.bend` の `main` は
`index(10, 5, 5)` を計算します。

```bend
def index(+n: U32, +x: U32, +y: U32) -> U32:
  (y * n + x : U32)

def main() -> U32:
  index(10, 5, 5)
```

`bend intermediate/minesweeper/nxn_geometry.bend` の出力は `55` です。
左上を(0,0)、xを列、yを行とし、行優先で `i=y*N+x` を計算します。
この `index` は有効な座標を受け取ることが前提です。外部のクリックには
`checked_index` を使い、無効なら `None` にします。

Bendの `Array.new` の深さ `d` は `2^d` 個の格納領域を表します。
10×10では `d=7` なので物理的に128スロットありますが、
100..127はマスではありません。盤外クリックも勝利判定も、
必ず `0<=i<N*N` を確認してから処理しましょう。

## 座標の正しさとゲーム全体の正しさは別です

座標を正しく変換できても、地雷を開いてしまう0連鎖や、
旗だけで勝利する誤実装を防げるとは限りません。
そこで次の状態不変条件を独立に確認します。地雷数の保存、
開いたマスが安全であること、数字が近傍地雷数と一致すること、
公開済みマスが閉じないこと、勝敗確定後に操作できないことです。

`python3 -m unittest discover -s intermediate/tests -p 'test_nxn_game_invariants.py' -v`
で、2×2の全60初手と10×10の固定乱数6,000操作を検査できます。
ただしこれは**Python参照モデルの有限テスト**です。
BendのN×Nゲームエンジンが完成したことも、すべての入力について
`law` が証明されたことも意味しません。

## 地雷の内部表現を32ビット語へ分ける（参照モデル、PDF未統合）

N=10では100マスの地雷を単一のU32に格納できません。そこで
`intermediate/solutions/nxn_word_storage.py` は地雷集合を
`ceil(N*N/32)` 個の32ビット語へ分割する**独立Python参照モデル**です。
Bend版の盤面状態を実装する際の入力契約・期待値を先に固定します。

```python
from nxn_word_storage import pack, has, set_cell, unpack
words = pack(10, {31, 32, 99})
print(words)                                    # (2147483648, 1, 0, 8)
print(has(10, words, 32))                       # True
print(sorted(unpack(10, set_cell(10, words, 32, False))))  # [31, 99]
```

32番は**次の語の0ビット目**です。99番は4語目の3ビット目に対応します。
100〜127番は語の末尾に存在する28個の余剰ビットであり、地雷にできません。
これは`Array.new`で確保される**余剰スロット**とは別の概念です。
N=10の可視状態Arrayは128スロット、地雷集合はU32の4語（128ビット）
という二種類の容量を区別します。

`validate`は語数・U32範囲・末尾の余剰ビットを検査し、
`set_cell`は元の語列を変更せず新しい語列を返します。
`has`は無効添字にFalseを返しますが、不正な格納形式は拒否します。
Pythonの2×2・3×3全配置と、10×10・100×100を含む境界・乱数操作を
`python3 -m unittest discover -s intermediate/tests -p 'test_nxn_word_storage.py' -v`
で検査します。**BendのN×N地雷配列・ゲーム遷移・GUI・全称証明は未実装**です。

演習として、31番と32番をそれぞれ立てた場合に語列のどの位置が
変わるか予想してみましょう。次に100番を設定する操作が拒否される
理由を説明してみましょう。

## N×Nの地雷集合をBendのU32配列へ移す（検証段階、PDF未統合）

Pythonの参照モデルを用意したら、今度はBendの配列で同じ操作を試してみましょう。
`intermediate/minesweeper/nxn_mine_words.bend` は、
地雷を32ビット単位の `Array<U32>` に分け、地雷の追加・削除・存在判定を行います。

```bend
def bit(+index: U32) -> U32:
  U32.shln(1, U32.to_nat(U32.mod(index, 32)))

def main() -> U32:
  read_bit(has(set_checked(set_checked(new(10), 31, True{}), 32, True{}), 32))
```

`bend intermediate/minesweeper/nxn_mine_words.bend` は `1` を返す設計です。
31番は第1語の最上位ビット、32番は第2語の最下位ビットです。
`set_checked` と `has` は必ず `Geo.valid_index` を確認するため、
100番や127番は10×10のマスとして扱いません。

`Array.new` は2の累乗個の語を確保します。10×10は論理的に4語で容量4語、
100×100は論理的に313語で容量512語です。
**余剰語をゲームの地雷と数えてはいけません。**
`new_checked` は範囲外のNを `None` として拒否します。
読み出しが返す配列とBoolの組は、配列の所有権を保つためです。

独立照合は `python3 intermediate/scripts/test_nxn_mine_words.py` で実施します。
2・3・4・10・17・100の各サイズ、31/32/63/64番の境界、
盤外添字、固定乱数による追加・削除を検査します。
**これは地雷格納層の有限テストであり、N×Nの勝敗・0連鎖・GUIや全称証明は対象外です。**

演習として、32番の地雷を消して31番を残す処理を書いてみましょう。
次に10×10の100番へ地雷を立てようとしても、地雷集合が変化しないことを
確認してみましょう。
