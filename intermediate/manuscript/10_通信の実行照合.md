# 第10章補稿：ループバック通信とメッセージ境界を実行で確かめる

## 必要性

TCPやUDPのAPI名を知っているだけでは、教材で変更したデータが本当に通信されたか、受信上限が何を意味するかまでは分かりません。ネットワークの結果は環境依存なので、外部サーバーへ依存しないループバックで小さな条件を検査します。

## 具体的なBendコードと実行結果

既存の配布用 `47_tcp_loopback.bend` は `TCP.send(client, "B")` と `TCP.recv(server, 1)` を使い、`B` と表示します。教材の演習どおり送信データだけを変えた一時コピーでは、次の結果を期待します。

| 対象 | 変更箇所 | 期待出力 |
| --- | --- | --- |
| TCP | `"B"` → `"7"` | `7` |
| TCP | `"B"` → `"BEND"`（受信上限1バイトのまま） | `B` |
| UDP | `"BEND-UDP"` → `"HELLO"` | `HELLO` |
| 区切り | `"ABC|DEF"` → `"ABCDEF"` | `1n` |
| 区切り | `"ABC|DEF"` → `"A|B|C"` | `3n` |

検査は `scripts/test_examples.py` が配布Bendコードを**上書きせずに**一時ディレクトリへ複製して行います。変更対象の文字列がちょうど1か所に現れることを確かめ、Bendの `--check-only` と実行出力の両方を比較します。合否は同じコミットのIntermediate textbook CIログで確認します。

## 仕組みと保証範囲

TCPの受信上限1は「送信したメッセージが1文字になる」という意味ではなく、「1回の読み取りで最大1バイトを得る」という意味です。`BEND`を送っても表示が`B`なら、残りのバイトまで取り出したわけではありません。また、文字列分割の `1n`・`3n` は**通信の実験ではなく**完成した文字列に対する純粋な `String.split` の検査です。通信上のフレーミングを実装したと扱いません。

本検証は単一プロセス内の `127.0.0.1` と小さなメッセージに限ります。パケット損失、途中切断、UDP切詰め、TCP送信の部分成功、多数の接続、他OS・外部ネットワークでの挙動を保証しません。利用環境でループバックが禁止されればテストが失敗する可能性があります。既存の通常版Bendサンプルの基準出力と、TeX・PDF・読者ZIPを変更しません。

## 演習

TCPの`recv(server, 1)`を増やさずに送信だけを長くすると、なぜ残りの文字が表示されないか説明してみましょう。次に、TCPで受け取った断片を区切り文字まで結合する方法を考え、UDPではメッセージ境界と配送保証のどちらが残る課題か整理してみましょう。
