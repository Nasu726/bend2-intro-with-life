# 第6章補稿：IOの結果と失敗を読む

> 編集状態：本文統合前の補稿です。プレビューPDFにはまだ反映していません。

## ゲームの規則は正しいのに、なぜファイル保存は失敗するのか

マインスイーパーの「旗があるマスは開かない」という規則は、同じ入力なら同じ結果を返せます。ファイル保存は違います。保存先が存在しない、アクセス権がない、空き容量が足りない、といった理由で、**同じプログラムでも環境によって失敗する**ことがあります。

前巻では `do` を使って画面へ値を出力しました。本章では「処理の結果」と「処理が成功したか」を意識して、Bend 2の `IO` と `Result` を読みます。使えるAPIをただ列挙するのではなく、何が返り、いつ終了し、どこでエラーを扱うのかを確認しましょう。

## 1. IOの中で値を受け取る

まず `08_args.bend` を読みます。

```bend
def main() -> IO(Unit):
  do IO<Unit>:
    xs: List<String> <- IO.args()
    IO.print(Nat.show(List.length(&1, String, xs)))
```

`IO.args()` は起動時の引数を取得します。返されるのは、プログラムの中ですでに分かっている定数のリストではなく、実行したときの環境から得るリストです。`do IO<Unit>` の中で `xs` に結果を受け取り、要素数を文字列に変換して表示しています。

ここで、`=` と `<-` の役割を区別してください。前巻の純粋関数では、値を作って次の計算へ渡していました。ここでは、`IO` という効果を持つ処理から結果を受け取っています。

`List.length` と `Nat.show` 自体は純粋な計算です。**副作用のある取得はIO、その結果の加工は普通の関数**、という分離が見えてきます。ゲームなら「実際の時刻を読む」はIOですが、「制限時間を超えたか比較する」は純粋関数にできます。

## 2. 成功するとは限らない処理の二段階

次は `11_random_io.bend` です。

```bend
def main() -> IO(Unit):
  do IO<Unit>:
    random_value: U32 <- IO.try(U32, IO.random_u32())
    IO.print(U32.show(random_value))
```

乱数の取得も環境に依存する操作です。実際の `IO.random_u32()` は失敗し得る効果を扱うため、`IO.try` で値を取り出し、失敗した場合は処理を中断する形にしています。

ここで大切なのは、**「IOの計算であること」と「失敗する可能性があること」は異なる話**だという点です。画面に文字列を出す、引数を読む、ファイルを開く、といった操作はすべてIOに関わります。しかし、どんな失敗を型で表すかはAPIごとに違います。関数名だけで「きっと値が返る」と判断せず、`bend base` で返り値の型を確かめます。

```sh
bend base IO.try
bend base IO.random_u32
```

初心者のうちは失敗したときに即終了するだけでも十分な場面があります。しかし実際のゲームでは、保存に失敗したらエラーを表示してゲームを続けたいこともあります。その場合、失敗を `Result` として受け取り、`match` で分岐する設計が必要です。

## 3. Resultを使うと処理の分岐が見える

`19_environment.bend` は環境変数 `PATH` の長さを取得する例です。`IO.get_env` から受け取った結果を、次の関数へ渡しています。

```bend
def env_length(value: Result<&1, &1, U32 & String, String>) -> Nat:
  match value:
    case Done{s}:
      String.length(s)
    case Fail{problem}:
      0n
```

`Done{s}` なら取得した文字列の長さを求めます。`Fail{problem}` なら0を返します。ここでは失敗した理由を使っていませんが、失敗を単に無かったことにしているわけではありません。呼び出し側が「取得できなかった場合は0と数える」と**明示的に決めた**処理です。

ただし、実際の保存処理で同じことをすると、重大な失敗を隠してしまうかもしれません。統計用の値が未取得であることと、ゲームの保存ファイルが壊れたことを、同じ「0」で扱うべきではない場面があります。失敗を返す型やエラーメッセージを、用途に応じて選びます。

この関数が `IO` ではなく `Nat` を返していることにも注目してください。**取得の仕事は外側のIO、成功・失敗の意味を解釈する部分は純粋関数**になっています。

## 4. Fileでは「値を返す」以外に守ることがある

ファイル操作では、失敗への対処に加え、**開いたファイルを閉じる**ことも必要です。これまでのアフィン性が実際に役立つ場面です。

`12_file_write.bend` を見ると、`File.open` でファイルを開いた後、`File.write` へファイルハンドルを渡しています。書き込みの結果は単なる `Result` ではなく、ファイルハンドルと結果の組です。

```bend
def close_after_write(
  r: File & Result<&1, &1, U32 & String, Unit>
) -> IO(Unit):
  (file, status) = r
  match status:
    case Done{value}:
      File.close(file)
    case Fail{error}:
      do IO<Unit>:
        Unit <- File.close(file)
        IO.die(Unit, 1, "Could not save sample_board.txt")
```

ここでは成功・失敗のどちらの分岐でもファイルを閉じています。**成功すれば閉じるが、失敗すると閉じない**という実装にしないためです。

さらに `13_file_read.bend` は、書き込んだファイルを読み込みます。読み込み後も、成功と失敗の両方でファイルを閉じてから、内容を返すか処理を終了します。二つの例は独立したプログラムなので、順番に同じ書き込み可能なディレクトリで実行してください。

```sh
bend examples/12_file_write.bend
bend examples/13_file_read.bend
```

前者で `sample_board.txt` を作成し、後者で内容を表示します。CIでは実際に保存してから読み戻し、文字列が一致するかを検査します。**型検査だけでファイルの読み書きが成功したと判断していません。**

この例を実行する前に、現在のディレクトリに同名ファイルがないか確認してください。サンプルの目的はファイルの取り扱いを学ぶことであり、既存ファイルを上書きする練習ではありません。

## 5. ゲームのどの部分をIOにするか

マインスイーパーを組み立てるときは、次のように処理を分けられます。

| 処理 | 主な責務 | なぜ分けるのか |
| --- | --- | --- |
| 旗・公開・勝敗の判定 | 純粋関数 | 同じ盤面と操作に対し同じ結果を出し、lawや実行テストで調べやすい |
| 乱数の取得・現在時刻 | IO | 実行環境によって結果が変わる |
| ファイルの書き込み・読み込み | IO | ファイルの有無や権限などで失敗する |
| 保存文字列の組み立て・読込結果の検証 | できる限り純粋関数 | ファイルを実際に開かずに、妥当性と失敗時の扱いをテストできる |
| ウィンドウへの描画とイベント受信 | IOを伴う境界 | 画面での操作は実機確認が必要 |

`IO` を避けることが正義なのではありません。副作用が必要な仕事は素直にIOで書きます。ただし、**データを加工するだけの仕事までIOへ押し込むと、テストする際に余分な準備が必要**になります。標準ライブラリの戻り値を読み、最も単純に責務を分けることが大切です。

## 6. 確認問題と次へのつながり

1. `IO.args` で取得した結果を、`List.length` が数えられるのはなぜでしょうか。`List.length` 自体にIOが必要でしょうか。
2. `19_environment.bend` で環境変数が見つからない場合は何が返りますか。これと、失敗したことを呼び出し側へ伝える `Result` をそのまま返す設計はどう違いますか。
3. `12_file_write.bend` の失敗分岐から `File.close` を削除する案を考えてみましょう。型検査・リソース管理・ユーザーへの通知の三つの観点で問題を挙げてください。
4. プレイヤーが「保存」を選んだ場合、マインスイーパーの純粋な盤面データを文字列にする処理と、実際にファイルを開いて書き込む処理は、どちらから先にテストできますか。

この章は、`IO`・`Result`・`File` のすべてを暗記することを目標にしていません。処理の結果を見て、**どこで失敗するか、そのとき何を片付けるか、どこまでを純粋関数で調べられるか**を説明できることが到達点です。

### 検証の範囲

環境変数の例は型検査と実行を、Fileの例は実際の書き込み・読み戻しを検査しています。一方、ディスク容量不足やアクセス権エラーを実際に発生させたすべての失敗経路は、まだ検証できていません。教材が保証することと、実装上追加検証が必要なことは区別します。
