# 第8章補稿：時計の前後関係と待機時間の境界

## なぜ測り直すのか

`IO.sleep(20)` は「20ミリ秒待つよう要求する」操作であって、「測定結果が必ず20になる」保証ではありません。ゲームのタイマーを作るときは、要求時間と実際の経過時間を区別しましょう。第8章の `46_elapsed_clock.bend` は20ミリ秒の一例です。ここでは0・20・100ミリ秒を比較します。

## 実行できるBendコード

`intermediate/scripts/fixtures/clock_intervals.bend` では次の形を三回繰り返し、`IO.now()` の前後の値を表示します。待機時間だけを0・20・100に変えます。

```bend
start: Nat <- IO.now()
Unit <- IO.sleep(20)
finish: Nat <- IO.now()
Unit <- IO.print(Nat.show(start))
IO.print(Nat.show(finish))
```

実行手順は次の通りです。

```sh
python3 intermediate/scripts/test_clock_intervals.py
```

PythonのテストはBendの型検査を行い、Bendプログラムを三回実行します。Pythonは時計の値を生成するのではなく、Bend自身が出力した六つの時刻を検査します。

## 実行結果として確認すること

一回の実行は整数六行です。二行ずつが0・20・100ミリ秒の待機前後の時刻です。例えば最初の二行を `a`, `b` とすると、`b - a` が観測経過時間になります。時刻は実行ごとに変わるため、固定した六つの数を正解とはしません。

検証用PR #82のCIでは、Bend型検査と3回の実行照合が成功しました。検証では時刻が後戻りしないこと、20ミリ秒要求の観測値が10ミリ秒以上、100ミリ秒要求が50ミリ秒以上であること、三つの観測時間の合計が外側の単調時計で測ったプロセス全体の時間を大きく超えないことを確認します。下限を要求時間の半分まで緩めるのは、特定のミリ秒値との完全一致を避けるためです。これらはLinux CI上の有限な受入条件であり、全OSでの時刻精度・待機保証を証明するものではありません。

## 仕組みと演習

`IO.now()` は `Nat` を返し、差の計算には `Nat.sub` を使えます。ただし自然数の減算だけを表示すると、時計が逆行しても差が0に丸められて見逃す可能性があります。この検証では生の時刻を二つとも出し、Python側で `start <= finish` を確かめます。

まず0・20・100ミリ秒を三回ずつ測り、観測値が毎回一致するか確認してみましょう。次に20を50に変え、テスト側の期待する待機時間と下限も更新してみましょう。「20ミリ秒待つ」という指定と「必ず20ミリ秒経過した」という主張の違いを説明してみましょう。

> 第8章には`55_clock_intervals.bend`による0・20・100ミリ秒の節がTeX・PDF・読者ZIPへ**統合済み**です。Bendの3試行と型検査は検証CI #40950714524、および正本先端`3139a27e`のIntermediate textbook CI #41041598768で回帰成功しました。本補稿自体とテスト専用fixture、解答は読者ZIPに入れません。`46_elapsed_clock.bend`も変更しません。

## 追加実習：待機時間を変えたときの検証（2026-10-31）

**必要性：** 元の0・20・100ミリ秒の結果を暗記しても、別の待機時間へ変更したときの確認方法は身に付きません。第8章の学習用コードを変更せず、テストだけで一時的な二つのBendプログラムを作って、予想と実測を比較します。

**具体的なBendコード：** `55_clock_intervals.bend` と同一の検証fixtureから、`Unit <- IO.sleep(20)` を `Unit <- IO.sleep(50)` に変えた版と、`Unit <- IO.sleep(100)` を `Unit <- IO.sleep(200)` に変えた版を別々に生成します。前後の `IO.now()` を出力する六行のコードと、他の待機時間はそのままです。

```sh
python3 intermediate/scripts/test_clock_intervals.py
```

**実行結果の読み方：** 前者は要求時間が `0/50/100`、後者は `0/20/200` ミリ秒です。時刻の絶対値や経過時間を固定値とは扱いません。テストは一時コピーをそれぞれBendで型検査・実行し、生の六時刻が逆行しないことを確かめます。Linux CIでの有限受入下限は、前者の50ミリ秒区間で25ミリ秒、後者の200ミリ秒区間で100ミリ秒です。観測区間の合計とプロセス全体の単調時計も照合します。**追加変種の成功は新しい検証CIの終了後に確定**し、OS全般の厳密な待機時間保証には一般化しません。

**仕組み：** テストは `src/55_clock_intervals.bend` と元fixtureの内容一致を最初に確認し、置換箇所が一意であることを検査します。配布コードは書き換えません。`Nat.sub` で負の差を隠す代わりに、生の時刻の順序と差を独立に確かめます。

**演習：** 20を50に変更した場合、元の20ミリ秒版と観測時間が毎回どちらの順に並ぶか予想してから実行してみましょう。実際にはスケジューリングで逆転し得る理由を説明してみましょう。次に100を200に変えた版で、要求時間と測定値が一致する必要がないことを確認してみましょう。
