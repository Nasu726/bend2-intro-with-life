## 追加検証：読み込んだバイトの値と順序

第7章TeXには、2バイトずつ4回読んで長さを表示する学習用コードが既に収録されています。しかし長さが正しくても、読み込んだ値や順序が正しいとは限りません。そこで**学習用コードと従来の検証fixtureを変えず、追加のテスト専用Bend fixture** `binary_chunks_values.bend` を用意します。配布サンプルとのバイト単位一致を維持します。

~~~bend
def digest_step(acc: U32, byte: U32) -> U32:
  (acc * 257 + byte + 1 : U32)

def digest_length(is_empty: Bool, is_single: Bool) -> U32:
  match is_empty:
    case True{}:
      0
    case False{}:
      match is_single:
        case True{}:
          1
        case False{}:
          2

def report_chunk(bytes: List<&2, U32>) -> IO(Unit):
  +digest = List.foldl(~&2, ~U32, ~U32, ~digest_step, bytes, 0)
  +length = digest_length(U32.is_lt(digest, 1), U32.is_lt(digest, 257))
  do IO<Unit>:
    Unit <- IO.print(U32.show(length))
    IO.print(U32.show(digest))
~~~

各回に「読み取った長さ」と「値の指紋」を1行ずつ表示します。今回の読み取り上限は2バイトです。**BendのListはアフィンなので、同じbytesをList.lengthとList.foldlに続けて渡すと二重消費となり型検査に失敗します。** そこで純粋計算の束縛を `do IO` の外に置き、1回だけfoldlして指紋を求め、0なら長さ0、1〜256なら長さ1、258〜66048なら長さ2と一意に復元します。+digestは複数回使うU32の共有を明示します。各バイトbをb+1（1〜256）に変換し、257進数として左から畳み込めば、**長さ0〜2の各バイト列に異なる値**を割り当てられます。2バイトでも最大値は66048でU32を超えません。したがって、長さと指紋がともに一致すれば、この上限2バイトの条件では内容と順序まで一致します。任意長のファイルに対する暗号学的ハッシュではありません。

検証PR #100の修正済みCI #40950714524では、4系列×長さ0〜5の24件のBend型検査・実行、65,793通りの長さ0〜2の指紋の一意性、旧配布サンプルの実行、欠損ファイルの拒否が成功しました。アフィンな`bytes`を二重消費しないため、`+digest`と`+length`の純粋な定義は`do IO`より前に置きます。これは`List.length`と`List.foldl`で同じアフィンなリストを二度消費できないことへの対処です。

さらに、**終端を観測したことと、指定回数だけ読み終えたことは違う**と確かめるため、テストの入力を4系列×長さ0〜9の40件へ拡張します。4回の読込上限は合計8バイトです。0〜6バイトでは4回目が空ですが、7〜9バイトでは4回目は空ではありません。長さ8と9の入力が同じ先頭8バイトを持つとき、Bendから見える4回分の長さ・指紋は同一で、9バイト目が未読であることをまだ判定できません。これは`File.read_bytes`が「最大量」を読むという性質の実例です。拡張40件の成否は検証CIで判定し、配布済みの0〜5バイトの表と`54_binary_chunks.bend`は変更しません。

**演習：** バイト列[0,10]と[10,0]を257進の計算で比較し、指紋が異なることを確かめてみましょう。次に読み取り上限を3バイトにしたとき、このU32の計算が常にオーバーフローしないか調べてみましょう。

## 仕組みと限界
`File.read_bytes` は `File & Result<..., List<...,U32>>` を返します。1回目の返り値に含まれるハンドルを2回目に渡すため、読み取り位置が進みます。`Done` で長さ0のリストが返ると、今回の通常ファイルでは終端に達したことを確認できます。元の長さ5では3回目に1バイト返るため、従来の3回だけでは終端を直接観測できませんでした。4回目の長さ0で終端を確認します。ただし、この有限テストは通常ファイルの0〜5バイトだけを対象とし、パイプ・ソケット・途中の短い読み取り・全OSに対する保証ではありません。長さだけでは内容の一致を証明できないため、既存の `45_binary_file.bend` と実ファイルのバイト照合も必要です。

## 2026-10-31追試：6回目でも残る未読の末尾

**必要性：** 5回の `File.read_bytes(file, 2)` では先頭10バイトしか観測できません。同じ先頭10バイトを持つ10バイトと11バイトのファイルは、5回目まで同じ出力です。6回目に空リストが返るか、1バイトが返るかを比べてみましょう。

**実行できるBendコード：** 配布済みの `54_binary_chunks.bend` を変更せず、テスト専用の `binary_chunks_values.bend` に次の分岐を追加します。5回目の結果に含まれるハンドルを6回目へ渡すので、アフィンな `File` を二重に使いません。

~~~bend
def after_fifth(result: File & Result<&1, &1, U32 & String, List<&2, U32>>) -> IO(Unit):
  (file, status) = result
  match status:
    case Done{bytes}:
      do IO<Unit>:
        Unit <- report_chunk(bytes)
        sixth: File & Result<&1, &1, U32 & String, List<&2, U32>> <-
          File.read_bytes(file, 2)
        after_sixth(sixth)
    case Fail{error}:
      do IO<Unit>:
        Unit <- File.close(file)
        IO.die(Unit, 1, "fifth byte read failed")
~~~

**実行結果（検証済み）：** 10バイトでは6回目の長さは0、11バイトでは1、12・13バイトではどちらも2です。同じ先頭12バイトを持つ12・13バイトでは、6回の長さと257進指紋が完全に一致します。独立Pythonオラクルが作った4系列×長さ0〜13の**56条件**について、Bendの型検査・実行、6組の長さ・指紋、元ファイル不変性を検証PR #121のCIで照合し、正本`1b3d108d`に統合済みです。これは通常ファイルの有限検査です。

**仕組み：** 6回の読み取り上限は合計12バイトです。空リストを観測していない限り、この通常ファイル実験では終端到達を断定できません。任意長ファイルに対する固定回数EOF保証ではなく、パイプ・ソケット等での短い読み取りも一般化しません。
