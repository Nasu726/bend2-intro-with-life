## 数字を見つけただけでは推論器に渡せません

三数字のBend全候補列挙器は、公開数字の位置ではなく、未知マスの**六ビット集合**を受け取ります。盤面の地雷の正解を知っているゲーム内部から直接集合を作ると、推論器が本当に公開情報だけで答えたのか分からなくなります。そこで、公開済みの `(マス番号, 数字)` 三組から入力を作る処理を分離します。

## 公開情報をBendの引数へ変換する

まずリポジトリの検証用Pythonコードを動かします。これは読者ZIPに収録するBend本体ではなく、**Bendに渡す値を独立に点検するための参照実装**です。

```python
from nxn_three_clue_adapter import from_public_clues

opened = ((0, 1), (2, 1), (7, 1))
request = from_public_clues(3, opened, mine_count=2)
print(request.cells)
print(request.bend_arguments())
```

```text
(1, 3, 4, 5, 6, 8)
(7, 13, 62, 1, 1, 1, 2, True)
```

`cells` の並びが、ビット位置0〜5と実盤面の番号の対応です。`masks` の7・13・62は、それぞれ公開数字0・2・7の**未公開の隣接マス**を表します。公開済みマス自身は集合に入れません。

この引数は既存の `minesweeper/nxn_public_three_small.bend` の `infer` に対応します。

```bend
def main() -> U32:
  score(infer(7, 13, 62, 1, 1, 1, 2, True{}))
```

```sh
bend intermediate/minesweeper/nxn_public_three_small.bend --check-only
bend intermediate/minesweeper/nxn_public_three_small.bend
# 341
```

表示の341は候補2通り・確定安全ビット14・確定地雷ビット1の符号化です。六ビットの14は盤面の3・4・5番に対応します。真の地雷配置やプレイヤーの旗は、変換関数の引数にありません。

## 六ビットの境界と地雷総数

**六ビット列挙器は必ず64通りを調べます。** 未知マスが五つしかないときに残り一ビットを何となく0で埋めると、列挙器はそのビットにも地雷を置き得ます。そこで今回の変換器は、三数字に接する未知マスが**ちょうど六つ**でない場合、`None` を返して扱わないことにしました。一般N×Nのソルバーへ拡張したわけではありません。

また、盤面に未公開マスが六つより多ければ、三数字に接しない場所にも地雷があり得ます。その場合、盤面全体の地雷総数を六ビットの地雷数と同一視してはいけません。変換器は `use_total=False` にし、局所的な三数字だけで分かる結論を返す設計です。これは**健全だが不完全**な推論です。総地雷数を使った、より強い推論は別の一般ソルバーの仕事になります。


## 公開数字が四つ以上ある場合

公開数字が増えると、三つだけを選んだ推論器を何度も利用できます。ただし、**選ばなかった公開マスを未知マスとして数えてはいけません**。例えば4×4盤面で0・1・2・4番が開き、それぞれ0・0・1・1を示す場合を考えます。

```python
from nxn_three_clue_adapter import from_public_board

opened = ((0, 0), (1, 0), (2, 1), (4, 1))
requests = from_public_board(4, opened, mine_count=2)
for request in requests:
    print(request.cells, request.bend_arguments())
```

```text
(3, 5, 6, 7, 8, 9) (2, 15, 50, 0, 1, 1, 0, False)
(3, 5, 6, 7, 8, 9) (6, 15, 50, 0, 1, 1, 0, False)
```

この二つの入力を、既存Bendの `infer` にそれぞれ渡します。独立全列挙で照合した結果は、順に `Forced{safe=2, mines=0, models=6}` と `Forced{safe=6, mines=0, models=4}` です。いずれも6ビットの局所結果なので、`cells` を使って盤面の番号へ戻します。

```python
from nxn_three_clue_adapter import combine_public_decisions

decisions = ((2, 0, 6), (6, 0, 4))
print(combine_public_decisions(zip(requests, decisions)))
# ((5, 6), ())
```

5・6番は、少なくとも一つの三数字推論から確実に安全だと分かります。**候補数6と4を足して10通りとは言いません。** 二つの推論が調べる候補は同じ公開盤面に由来し、独立した場合分けではないからです。ここでは安全・地雷の確定結果だけを和集合にまとめます。局所的な矛盾は `None` で区別しますが、すべての三数字が個別に整合していても、盤面全体の整合性が証明されたわけではありません。

公開数字は最大24個まで受け付け、三つ組を列挙します。六つの未知隣接マスを作れない三つ組は採用しません。盤面の未公開マスが六つより多い場合、総地雷数2を六ビットの地雷数と誤認しないよう、各入力は `use_total=False` にします。このため推論は健全でも不完全であり、一般N×Nソルバーではありません。

**演習：** 上の4×4例で、`(1, 0)` を取り除いてからもう一度入力を作り、利用できる三つ組と確定安全マスを比べてみましょう。さらに、各入力の `cells` が、どの公開マスも含まないことを確かめてみましょう。

## 演習

2. 4×4で公開マスを0・1・5番とし、三つの数字を1にしてみましょう。六つの未知隣接マスは得られますが、盤面全体の地雷総数2をそのまま六ビットへ渡してはいけない理由を考えてみましょう。

## 公開済みのマスから未知の近傍をBendで取り出す（検証用追補）

六ビットの推論器へ値を渡す前に、「公開済みの数字の周囲で、まだ開いていないのはどこか」を求める必要があります。地雷の正解を参照して集合を作ってしまうと、運ゲー無しという主張を検査できません。

`minesweeper/nxn_public_neighbors.bend` は、既存の `nxn_neighbors.bend` で盤面内の隣接マスを列挙し、`nxn_public_subset.bend` の `contains` で公開済みのマスを除きます。既存の近傍列挙・集合判定を再利用するため、座標計算を重複実装しません。

```bend
def unknown_neighbors(+n: U32, +index: U32,
                      +revealed: List<&2, U32>) -> List<U32>:
  if_revealed(Sets.contains(revealed, index), n, index, revealed)

def main() -> U32:
  Neighbors.count(unknown_neighbors(3, 7, [0, 2, 7]))
```

```sh
bend intermediate/minesweeper/nxn_public_neighbors.bend --check-only
bend intermediate/minesweeper/nxn_public_neighbors.bend
# 5
```

3×3の公開マスが0・2・7なら、7番に隣接する未知マスは3・4・5・6・8の五つです。ここで返すのは**マス番号のリスト**であり、六ビットのマスクではありません。後段で未知マスを六つに並べ、各番号をビット位置に対応付けてから三数字の推論器へ渡します。公開されていない位置を「公開数字」として指定した場合は空リストを返します。これは確定安全という意味ではありません。

**演習：** 公開マスを `[0, 1, 2, 4]` に変え、4×4盤面の0番・1番・2番・4番それぞれについて、未知の隣接マスを予想してから確かめてみましょう。さらに、公開されていない3番を指定した場合の空リストと、すべての隣接マスを開いた場合の空リストが、同じ意味ではないことを説明してみましょう。

**検証の境界：** `scripts/test_nxn_public_neighbors.py` は2×2〜100×100の有限34ケースについて、Bendの型検査・実行結果を独立した座標オラクルと比較するためのものです。CIが成功するまではBendの実行成功を主張しません。入力の公開マス一覧は重複なし・範囲内・昇順であることを前提とし、公開数字の値そのものや複数制約の組み立て、一般N×Nの完全ソルバー、GUI実機を検証するものではありません。TeX・PDF・読者ZIPへの統合も別工程です。
