## 必要性と責任分離

4×4の旧 `gui.bend` は固定盤面 `Start.new(33)` を起点にする教材です。初手前に地雷位置を保持しない確定仕様の10×10版へ、そのまま置き換えることはできません。まずGUIの座標・マウスボタンをゲームの操作へ変換する**純粋な境界**を作り、表示の実装とは分離して検証します。

新規 `minesweeper/nxn_gui_adapter.bend` は `nxn_lazy_game.bend` の `Fresh{n,count,seed}` をそのまま利用します。初手前に地雷集合を生成しません。画面のクリック位置をセル番号へ変換した後、左ボタンだけ `Lazy.click`、右ボタンだけ `Lazy.mark` に渡します。その他のボタンと画面外座標はゲームを変更しません。右ボタンはFreshの間は無作用です。

## 具体的なBendコード

```bend
def pointer_n(game: Lazy.Game, n: U32, x: U32, y: U32, button: U32) -> Lazy.Game:
  mouse_index(cell_at(n, x, y), game, button)

def pointer(game: Lazy.Game, x: U32, y: U32, button: U32) -> Lazy.Game:
  pointer_n(game, 10, x, y, button)

def reset_gui(seed: U32) -> Lazy.Game:
  reset(10, 10, seed)
```

1マス32×32画素なので10×10画面は320×320画素です。左上(0,0)はセル0、右下(319,319)はセル99、(320,0)は画面外です。任意N（2〜100）について `(y // 32)*N + (x // 32)` を使います。境界外は `Maybe.None` で拒否し、実際のクリック処理へ到達させません。

`scripts/test_nxn_gui_adapter.py` は独立したPython座標オラクルから18件の境界値、固定10×10のラッパー3件、13件のイベント列の期待値を作ります。Bend 2でそれぞれ型検査・実行し、検証PR #87の全CI成功を確認しました（CI #40781258079）。開始前の画面外クリック、右クリック、未知ボタンは `Fresh` を保ち、初手左クリック後は既存のN×N遅延生成・連鎖・終局処理へ進みます。これは有限の入力列についての成功であり、OS上の描画・操作を確認した結果ではありません。

## 2026-10-29：イベント配送をゲームに接続する（有限検証済み）

座標変換だけでは、押下・解放・リセット・ウィンドウ終了を区別できません。`nxn_gui_events.bend` ではBendの`Event`を純粋なゲーム状態遷移へ変換します。

```bend
def event(e: Event, game: Lazy.Game, seed: U32) -> Maybe<Lazy.Game>:
  match e:
    case Close{}:
      None{}
    case Key{27, True{}}:
      None{}
    case Key{114, True{}}:
      Some{GUI.reset_gui(seed)}
    case Key{82, True{}}:
      Some{GUI.reset_gui(seed)}
    case Mouse{x, y, button, True{}}:
      Some{GUI.pointer(game, x, y, button)}
    case _:
      Some{game}
```

EscとCloseは`None`、R/rは地雷集合を作らない`Fresh`へ戻し、マウスの押下だけを既存の座標変換へ渡します。例えば、リセット後の`snapshot(...,0)`は`300`、Closeは`None`です。16種類の入力列を独立Python期待値とBend型検査・実行で照合し、検証PR #88の全CI成功を確認しました（CI #40795728371）。

マウスの押下と解放、初手後のリセット、RとEscの違いを試してみましょう。これは`App.run`でOSイベントを受け取った実機試験ではなく、描画用`Image`も未実装です。TeX・PDF・読者ZIPへの反映は別途同一版検証が必要です。

## 次の実装単位：描画とOSイベント接続の検収契約

入力とイベントの有限検証が成功しても、画面が描けるとは限りません。旧4×4 `gui.bend` の `view` は表示用配列を `Array.clone` して画像を組み立てています。10×10版でも、**ゲーム状態を保持したまま公開セルだけを表示する**責任を独立させます。

- `Fresh{n,count,seed}` は全セルを未公開として表示し、描画やマウス移動を理由に `Lazy.generate` を呼びません。地雷配置は最初の有効な左クリックまで存在しません。
- `Active` の表示は公開セルの `Hidden`／`Flag`／`Open{clue}` のみを参照します。地雷真値は描画や推論へ流しません。表示のためにゲームの所有権を消費しないよう、必要な可視配列だけを複製し、状態を返します。
- 入力座標の契約は32画素単位・有効範囲 `0 <= x,y < 320` です。Bend `Image` の四分木表現と実ウィンドウの寸法が一致するかは、描画実装時に検証します。未確認のパディング・拡大率を既定仕様として断定しません。
- 左押下、右押下、R/r、Esc、Closeの状態遷移を実際の `App.run` に接続します。押下・解放、盤外、初手、旗、勝敗、リセットをGUI上で再試験し、`Fresh` への復帰で地雷集合が残らないことを確認します。

既存の有限検証では、座標18件・10×10ラッパー3件・ゲーム操作列13件、イベント列16件が成功しています。**画像のピクセル一致、ウィンドウ生成、OSイベントの配送、10×10実機操作、一般N×N運ゲー無し性は未検証**です。これらの実装・検証後に限り第21章のTeX本編と読者ZIPへ同期します。

演習として、リセット後に全セルが未公開へ戻ることと、初手前の右クリックで盤面が生成されないことを、表示と内部状態の両方で確かめてみましょう。

## 2026-10-29：10×10のImage描画とApp.run入口（検証候補）

### 必要性

入力イベントをゲームへ渡せても、画面に公開情報を描かなければ遊べません。一方で、画面を描くたびに地雷を再生成したり、隠された地雷位置を描画側へ渡したりしてはいけません。そこで、`nxn_gui_render.bend`では`Fresh`の描画を未公開セル100個だけから作り、`Active`では`Array.clone(Game.Square, cells)`で可視セル配列を複製します。地雷を保持する元のゲーム状態はそのまま返します。

### 具体的なBendコード

```bend
def view_session(session: Step.Session) -> Step.Session & Image:
  match session:
    case Step.Session{n, mines, cells, phase}:
      view_cloned(n, mines, phase, Array.clone(Game.Square, cells))

def view(game: Lazy.Game) -> Lazy.Game & Image:
  match game:
    case Lazy.Fresh{n, count, seed}:
      (Lazy.Fresh{n, count, seed}, fresh_picture())
    case Lazy.Active{state}:
      active_view(view_state(state))
    case Lazy.Invalid{}:
      (Lazy.Invalid{}, Pix{0})
```

`nxn_gui_app.bend`では`App.run(~Lazy.Game, ~App{view, tick}, ..., 512, 512, GUI.reset_gui(20261029))`を入口とし、既存の`Events.tick`へイベントを渡します。Imageは2の累乗の四分木なので、16×16タイルを描く128×128のImageを512×512画素へ拡大します。1タイルは32×32画素です。左上10×10タイル（320×320画素）のみ操作可能で、右側・下側の192画素は黒い余白とし、既存の座標変換でクリックを拒否します。各タイルには境界線と数字の7セグメント表示を置きます。

### 実行結果・検証境界

独立Python参照モデルでは、初手前の状態コードは`300`、seed `20261029`で左上を最初に開いたセルのコードは`10`（数字0）です。画素の期待値は、未公開セル内部`8689825`、数字0の背景`15658734`、右下の余白`0`です。13条件をBendのheadless実行で照合し、GUI入口を`--check-only`で型検査するテストを追加しました。**この補稿を作成した時点ではBend実行とApp.run型検査のCI結果は未確認**です。Python静的事前検査は成功しています。

## 2026-10-29：四分木サンプラーの照合順と検証範囲（検証候補）

`Image`をheadlessで検査する際は、`Qua`の四つの子から画素座標に対応する一つを選びます。Bend 2.0.39では、局所変数を定義した後にその変数を`match`する構造は型検査に失敗します。そこで`pixel_at_walk`に上下・左右のBoolを引数として渡し、最初に`match img`、次に`match bottom right`を行ってから座標を更新します。再帰には必ず`Qua`の直接の子を渡し、構造的減少を明確にします。

追加の4条件では、四分木`Qua{Pix{11}, Pix{22}, Pix{33}, Pix{44}}`を使い、2×2の左上・右上・左下・右下でそれぞれ`11, 22, 33, 44`を期待します。従来の13条件と合わせて17件です。**現時点では新しいBend型検査と実行結果は未確認**であり、成功したと断定しません。OSウィンドウの表示・イベント配送は引き続き実機検収が必要です。

演習として、四分木の右上・左下の座標を入れ替えると期待値がどう変わるか、`pixel_at`の引数を変えて確かめてみましょう。

## 2026-10-29：描画後の可視状態と旗の表示を照合する（検証候補）

### Bendコードと実行予定の結果

```bend

game = GUI.pointer(GUI.pointer(GUI.reset_gui(20261029), 0, 0, 0), 319, 319, 1)

# pairに含まれるゲームのセル99はFlag（snapshotは1）
```

### 演習

### 仕組みの説明：描画結果をもう一度調べる

Bendでは、計算した組をその場で直接分解する書き方が型検査で拒否されることがあります。今回の検証ハーネスでは、描画済みのゲームを受け取った後、もう一度描画してから、結果を**別の関数の引数**として渡します。

```bend
def view_twice_probe(pair: Lazy.Game & Image, index: U32) -> U32:
  (game, img) = pair
  view_probe(RENDER.view(game), index)
```

`view_probe`の引数として受け取った組は、関数内で`(game, img)`と分解できます。この形にすれば、再描画後のゲームの可視状態を検査する意図が明確になり、描画用のImageをゲームの地雷情報と混同しません。最初の検証CIでは計算結果を直接分解したため**型検査に失敗**しました。上の修正版も、Bend実行CIの成功までは検証候補です。

再描画した直後に`GUI.snapshot`で旗が残っているか確かめ、続けて同じセルを右クリックして旗を外したらどうなるかを比較してみましょう。


## 2026-10-30：GUI操作履歴の復元を作る（検証候補）

### 必要性

現行の10×10 GUIは初手前に地雷配置を作らず、最初の有効な左クリックで初めて生成します。そのため、ゲーム内部の地雷配列をそのまま外へ出して保存するのではなく、**同じシードから公開操作を再生する**方式を選びます。これは配布済みの4×4 CLI履歴保存の考え方をN×N GUIへ移す準備です。

### Bendコード

`minesweeper/nxn_gui_history.bend` は、表示中の `Lazy.Game` と逆順の操作履歴、初期シードを一緒に保持します。操作履歴は `2 * index + button`（左=0、右=1）で表します。画面外入力や中央ボタンは記録せず、Rのリセットでは過去の履歴を捨てます。

```bend
type Model is Type:
  Model{game: Lazy.Game, newest_first: List<&2, U32>, seed: U32}

def restore(+seed: U32, +entries: List<&2, U32>) -> Recovery:
  on_valid(Bool.and(Nat.is_le(List.length(&2, U32, entries), 512n),
                    valid_entries(entries)), entries, seed)
```

再生前に各操作が10×10の有効なセルとボタンに対応するか検査し、512操作を超える履歴は `Corrupt{}` として拒否します。有効なコードはセル0〜99とボタン0〜1から作る0〜199の200通りです。一部だけ適用した壊れた状態を返しません。`Fresh` での右クリックも再生可能ですが、地雷配置を生成しません。

### 実行結果と検証範囲

独立Pythonモデルの期待値では、シード `20261029` の初手左クリック `0`、セル99への右クリック `199` を再生すると、セル99の表示コードは `1`（旗）です。続けて `199` をもう一度再生すれば `0`（未公開）に戻ります。記録済みの不正コード `200`（セル番号100への左クリック）は `Corrupt{}` となり、検証上のコードは `600` と表します。

```sh
python3 intermediate/scripts/test_nxn_gui_history.py --static-only
python3 intermediate/scripts/test_nxn_gui_history.py
```

この16条件は、検証ブランチのBend型検査・実行が成功するまでは**期待値**です。X11でのキー入力、保存ファイルの読み書き、破損ファイルの取り扱いはこの段階の検査には含まれません。

### 仕組みの説明

`Model` はゲーム本体を保持する `Type` です。保存するのは内部の地雷配置ではなく、再生可能な小さな整数列に相当します。復元時は `GUI.reset_gui(seed)` から出発し、左クリック・右クリックを記録時と同じ順に適用します。初手の配置がシードとクリック位置で再現されるため、公開盤面の状態も同じになります。

### 演習

初手の前に右クリックを記録した場合、再生後も `Fresh` であることを確かめてみましょう。続いて、旗を二度操作した履歴 `[0,199,199]` と、リセット後の履歴を比較してみましょう。`[0,199]` と `[199,0]` では同じ数字を含んでいても操作順が異なることを確かめてみましょう。不正なセルコードを途中に入れた履歴が拒否される理由を考えてみましょう。

**残る実装：** この履歴基盤は現行 `App.run` の表示状態にはまだ接続しておらず、実際のFile保存・読込も未実装です。GUI保存・復元機能を完成と呼ぶのは、ファイル入出力とS/Lキー等のイベント、X11再起動後の復元を検証してからです。


## 2026-10-30：10×10 GUIの操作履歴をファイルへ保存する（検証候補）

### 必要性

直前のGUI操作履歴はメモリ内で再生できますが、アプリを終了すると消えてしまいます。途中まで遊んだ盤面を復元するには、初期シードと操作列を小さなファイルへ保存すれば十分です。隠し地雷の真値やメモリ上の配列を外へ保存する必要はありません。

### 具体的なBendコード

学習用モジュールは minesweeper/nxn_gui_store.bend です。BendのFile.open・File.write・File.read・File.closeを使用します。既存の4×4 CLI保存と同じFile APIですが、こちらは **10×10で0〜199の入力コード、最大512操作**に限定します。保存形式は BEND2-GUI-1|シード|操作0|操作1|END です。

~~~bend
def encode(entries: List<&2, U32>) -> String:
  match entries:
    case Nil{}:
      "END"
    case entry <> rest:
      U32.show(entry) ++ "|" ++ encode(rest)

def payload(+seed: U32, entries: List<&2, U32>) -> String:
  "BEND2-GUI-1|" ++ U32.show(seed) ++ "|" ++ encode(entries)
~~~

保存前に操作数・各コードの有効性を検査します。条件を満たさない場合、ファイルを開く前に拒否するので、既存の保存データを不用意に上書きしません。

読込時は版番号、整数シード、末尾END、各操作、合計512操作と4096文字以内を検査し、一つでも不正ならCorruptを返します。4096文字より長いファイルの先頭だけを有効な保存データとして誤認しないよう、4097バイト読み取る設計です。

## 2026-10-30：保存ファイルが存在しない場合にもGUIを止めない（検証候補）

### 必要性

S/Lキーを実装しただけでは、初回起動時にLを押したときに保存ファイルが存在しないことがあります。従来の`IO.try(File, File.open(...))`は開けない場合にプロセスを終了させるので、**通常の操作がGUI終了につながる**問題がありました。書込み不能時や、512操作を超えてしまった場合も盤面を保持する必要があります。

### 具体的なBendコード

```bend
def finish_open_read(opened: Result<&1, &1, U32 & String, File>) ->
  IO(History.Recovery):
  match opened:
    case Fail{error}:
      IO.pure(History.Recovery, History.Corrupt{})
    case Done{file}:
      do IO<History.Recovery>:
        result: File & Result<&1, &1, U32 & String, String> <-
          File.read(file, 4097)
        finish_read(result)
```

ファイルのopenの失敗を`Result.Fail`として分岐し、既存の`History.Corrupt`経路へ戻します。読込み中の失敗でも`File.close`を行い、現在のゲームを保持します。保存側も開く前の履歴の検査、書込み失敗時のclose、元の`History.Model`の返却を保ちます。

### 期待する実行結果

保存ファイルがない状態でLを押しても画面はFreshのまま、Sで保存に失敗しても現在の盤面は変化せず、正常保存してからLを押すと公開履歴が再生されます。破損テキスト、ファイルを装ったディレクトリも拒否します。これらのBend実行、X11実画面試験は検証PRのCI成功まで**未確認**です。

### 仕組みと演習

`IO.try`は失敗すると終了する一方、`File.open`の返す`Result`を自分で調べれば、失敗時の方針を決められます。ただし、現段階では失敗内容をユーザーに表示しません。読み取れない・壊れている・ファイルがない、を同じ「現在のゲームを維持する」にまとめています。保存失敗もGUIの通知なしで盤面を維持するため、失敗したことを利用者に示す表示は別の課題です。

保存ファイルを削除してLを押し、盤面が変化しないことを確かめてみましょう。続いて保存先をディレクトリに置き換えてSを押し、GUIが終了しないことを確かめてみましょう。正常な保存・再起動後の復元との違いを説明してみましょう。
