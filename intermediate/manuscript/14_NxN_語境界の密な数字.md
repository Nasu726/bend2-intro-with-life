## なぜ32ビット語の境界を意識するのでしょうか

10×10盤面には100マスあります。地雷の有無を32ビットずつ格納すると、31番は最初の語の最後のビット、32番は次の語の最初のビットになります。一方、プレイヤーにとってはどちらも普通の隣接マスです。**内部の格納境界をまたいでも、周囲の地雷を正しく数える**必要があります。

マス番号は左上から行優先で付けます。例えば41番は `(x, y) = (1, 4)`、31番は `(1, 3)`、32番は `(2, 3)` です。31番と32番の両方に地雷があれば、41番の数字には少なくとも2を加えます。

## 小さなBendコードで動かしてみましょう

`intermediate/minesweeper/nxn_clues.bend` の `main` は、次のように地雷0番・11番を置いて1番の数字を求めています（`Mines` は同ファイルで読み込んだ `nxn_mine_words.bend` です）。

```bend
def main() -> U32:
  read_count(clue(Mines.set_checked(Mines.set_checked(Mines.new(10), 0, True{}), 11, True{}), 1))
```

リポジトリのルートから実行してみましょう。

```sh
bend intermediate/minesweeper/nxn_clues.bend
```

期待する表示は `2` です。1番の座標は `(1, 0)` で、0番と11番はいずれも8近傍に含まれます。この `main` は実装の最小例です。31/32番の境界を含む多数の配置は、次の検証器で別に確かめます。

```sh
BEND_NXN_CLUE_BATCH_SIZE=64 python3 intermediate/scripts/test_nxn_geometry.py
```

Bend 2.0.38を使った2026-10-23の検証CIでは、次の結果を得ました。

```text
PASS Bend N x N geometry: 401 independent finite checks
PASS Bend N x N mine words: 306 independent finite checks
PASS Bend N x N clues: 533 finite independent checks
```

## 数字を数える仕組み

`nxn_clues.bend` は中心マスの周囲8方向を調べ、`Geo.neighbor(n, x, y, u, v)` で**非トーラス盤面の有効な隣接座標**かを判定し、`Mines.has` でその位置の地雷ビットを読み取ります。両方が真のときだけ `masked_bit` が1を加えます。例えば左端から1つ左へ進むと、`U32` の減算が折り返す場合があります。単に線形添字が有効かを調べるだけでは別の地雷を誤って数えるため、幾何学的な隣接判定が必要です。

また、`Mines.has` は地雷集合を返し直すAPIです。Bendでは資源を持つ値の所有権を考える必要があるため、`accumulate_read` が返された地雷集合と真偽値を受け取り、次の方向へ地雷集合を渡します。盤面サイズ `n` の二重消費も、`count_checked_parts(+n, words, +i)` で再利用可能な引数として受け取ることで避けています。

533件の実Bend照合はN=2・3・4・10・17・100を含み、数字0〜8、中心マス自身の地雷を数えないこと、盤面外の番号、31/32番・63/64番の語境界を検査します。Pythonで独立に計算した期待値と一致し、**533件すべてで型検査と実行照合が成功**しました（[検証CI #39939806466](https://github.com/Nasu726/bend2-intro-with-life/actions/runs/39939806466)）。

この結果は**有限個の数字計算**に限られます。N×Nのクリック・初手安全・0連鎖・勝敗・10×10 GUI・運ゲー無し生成を統合したBendゲームの検収や、任意のNに対する全称証明ではありません。
