# 第8章補稿：時計テスト自体を検査する

> 2026-11-01の検証候補です。これはリポジトリ側の編集・テスト資料であり、読者PDF・ZIPにはまだ収録しません。配布済みの`55_clock_intervals.bend`と第8章TeXは変更しません。

## 必要性

`IO.sleep(20)`の結果が毎回ちょうど20ミリ秒になると期待すると、正しいプログラムを誤って不合格にする可能性があります。逆に、待機処理が実行されなくなった場合や`IO.now()`が逆行した場合を見逃してもいけません。Bend本体を検査するPython側の判定器にも、正しい入力と誤った入力を与えて確認します。

## 実行できるBendコードと判定器

配布済みの`55_clock_intervals.bend`は、0・20・100ミリ秒の各待機の前後で`IO.now()`の生の値を出力します。実行は従来どおりです。

```sh
python3 intermediate/scripts/test_clock_intervals.py
```

Bendの6行出力は`validate_readings(lines, wall_ms, trial)`へ渡します。この関数はBendコードではなく、**Bendの出力を独立に評価するPythonオラクル**です。Bendがなくてもオラクルの反例を試せます。

```sh
python3 -m unittest discover -s intermediate/tests -p test_clock_validator.py -v
```

## 実行結果と反例

Python単体テスト10件では、待機0・20・100ミリ秒に対して経過時間がそれぞれ`0,10,50`となる境界例を合格させます。`5,31,120`のように要求時間と異なる観測値も合格させます。一方、6行以外、ASCII以外の数字、負数、逆行する時刻、20ミリ秒待機で9ミリ秒、100ミリ秒待機で49ミリ秒、プロセス全体の観測時間と矛盾する値を拒否します。`NaN`や無限大の外側時計値も拒否します。

この10件は**Pythonオラクルの有限な単体検査**です。実Bendの型検査・3試行は、既存の`test_clock_intervals.py`がCIで行う別の受入条件です。単体テスト成功だけで実機の時計精度を保証したり、Bendの実行が成功したと扱ったりしません。

## 追加の反例：測定区間の間で時計が飛ぶ

**必要性：** 0・20・100ミリ秒の三つの待機区間だけを合計して外側の時計と比較すると、区間と区間の間に発生した不自然な時計の飛びを見逃します。例えば生時刻が `0,0,100000,100020,100020,100120` で、外側のプロセス実行時間が200ミリ秒なら、待機区間の合計は120ミリ秒で従来の判定を通りますが、最初から最後までは100120ミリ秒も進んでいます。

**実コード：** 判定器では六つの値を保持し、三つの待機時間の下限を検査した後、`stamps[-1] - stamps[0]` と外側の `time.monotonic()` による経過時間を比較します。余裕幅1000ミリ秒は既存のままです。さらに `Nat.show` の出力として先頭ゼロのないASCII十進表記を要求し、異常に長い数値文字列（128桁超）や文字列以外の値を拒否します。

**実行結果：** Python単体テスト10件はローカルで全成功しました。従来の8件に加え、区間間の時計ジャンプと不正な数値表記を拒否します。実Bendの3試行とTeX/PDF/ZIPの一致は、検証PRのCIで別途確認します。

**仕組みと演習：** 非減少の六時刻なら、最初から最後までの差は各待機区間の和以上です。区間間の経過も含めて検査することで、待機区間だけが正常に見える反例を検出できます。三つの待機区間の差がそれぞれ`0,20,100`なのに、区間間で100秒進む入力を自分で作り、旧判定と新判定の違いを確かめてみましょう。

## 仕組み

6つの生時刻`a,b,c,d,e,f`の隣接するすべての値に対して非減少を検査し、待機時間は`b-a`、`d-c`、`f-e`で求めます。`Nat.sub`だけを見ていると逆行が0に丸められる場合があるため、生時刻の順序を先に調べます。20・100ミリ秒の緩い下限は10・50ミリ秒とし、0ミリ秒には正の下限を設けません。外側の`time.monotonic()`と比較する上限には余裕を設け、三つの待機区間だけでなく最初から最後までの経過を比較します。これらはLinux CIで待機処理の無視を検出するための受入条件であり、あらゆるOS・負荷条件での時刻保証ではありません。
