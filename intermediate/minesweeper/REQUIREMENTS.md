# マインスイーパー — 要件・法則台帳（実装の前に策定）

このディレクトリをゲーム実装の独立した単位とします。Bend 2公式
[GUIDE](https://github.com/bendlang/bend/blob/main/guide/GUIDE.md#laws-and-proofs)
の慣例に合わせ、`LAWS.bend` は要求、`game.bend` は実装、
`PROOF.bend` は証明です。法則は実装の都合で無断変更しません。
変更する場合は、ゲーム仕様の変更理由・既存の利用者への影響を明記します。

## 仕様の区分

| ID | 要件 | 状態 | 検査 |
| --- | --- | --- | --- |
| C-01〜C-04 | 隠す／旗を置く／外す、公開済みマスを変更しない | lawで定義 | `LAWS.bend` |
| C-05〜C-07 | 安全な未公開マスを開く、旗を保護する、表示済み数字を保つ | lawで定義 | `LAWS.bend` |
| B-01 | 有限盤面の外には隣接しない（反対側へ回り込まない） | 次段階 | 近傍の法則と境界テスト |
| B-02 | 地雷集合が固定されたあとは操作によって変化しない | 次段階 | 盤面不変条件 |
| B-03 | 公開済みの安全マス集合は公開操作で減らない | 次段階 | 公開操作の単調性 |
| B-04 | 安全マスを開いたとき、表示数字は実際の隣接地雷数と等しい | 次段階 | 盤面の数字 |
| B-05 | 旗や公開済みマスは通常の公開操作で不正に上書きされない | 次段階 | 操作の事前条件 |
| G-01 | 初手では地雷を踏まない（初手確定後に配置してよい） | 次段階 | 配置の契約と生成テスト |
| G-02 | 地雷を開くと敗北し、それ以降は通常操作で状態が変わらない | 次段階 | 終了状態 |
| G-03 | 地雷でないマスがすべて公開された場合に限り勝利 | 次段階 | 勝利の必要十分条件 |
| G-04 | 数字が0のマスを開いたら安全な近傍を連鎖公開する | 次段階 | 0展開の停止・境界 |
| P-01 | ソルバーには公開情報だけを渡す | 発展 | 入力型の分離と独立オラクル |
| P-02 | ソルバーが確実な手だけでクリアできた盤面のみ運ゲー無しとして採用する | 発展 | 生成・リプレイによる検証 |
| E-01 | GUIイベントの座標→操作変換、保存・復元とエラー処理 | 統合段階 | 純粋関数テスト＋実機試験 |

**重要：**「次段階」は未証明・未実装です。表内の自然言語の要件を
`law` に落としてから、各段階の実装を着手します。ゲームの正当性を
C-01〜C-07の証明だけで主張してはいけません。

## 開発・検証順序

1. 要件を表で確定し、`LAWS.bend`に機械検査可能な法則として記述する。
2. 仕様を変更せず`game.bend`を実装する。
3. `PROOF.bend`で **すべての法則** を同名の`def Laws.xxx`として証明する。
4. `bend intermediate/minesweeper/PROOF.bend --verdict`を実行する。
5. 法則が対象としていないGUI、IO、乱数を別途テストする。

`--verdict`はLeanで検証された小さいカーネルを用いる経路です。
未解決の証明穴、`@unsafe`、FFIに頼る証明を合格として扱いません。
`ALL PROOFS CHECK`を要求し、`LAWS.bend`が実際にimportされて
いることと、期待する法則が削除されていないこともCIで点検します。

## 教材の学習順

一つの公開マス（C系列）→境界と近傍（B-01）→盤面全体（B-02〜05）
→初手安全・勝敗・0展開（G系列）→GUI/IO（E系列）
→推測不要生成（P系列）の順に広げます。

最初は手動の小さな例を使い、各段階で失敗するテストも用意します。
`LAWS.bend`の人間による要件承認と、実装の証明を区別することが大切です。
