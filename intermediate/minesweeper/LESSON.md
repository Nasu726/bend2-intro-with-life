# 教材原稿案：要求を先に書き、1マスを実装する

> TeX第13・15〜17・21章へ段階的に統合するための草稿です。現行プレビューPDFには未反映です。
> 法則の総数はC・B・G系列を合わせて31件です。以下は段階別の学習順で説明するため、各節の保証範囲はその時点に限ります。

## 読者の疑問から始める

画面上のマスは「隠れている」「旗を置いている」「数字が見える」という
三つの状態を取ります。クリックしたときの振る舞いを、後から実装者の
判断で決めてしまうと、旗付きのマスを誤って開いたり、既に見えていた
数字を上書きしたりするかもしれません。

最初に次の表を**要件として確定**させます。

| 操作 | 入力 | 結果 |
| --- | --- | --- |
| 旗の切替 | Hidden | Flag |
| 旗の切替 | Flag | Hidden |
| 旗の切替 | Open(n) | Open(n) |
| 安全な公開 | Hidden, 隣接数n | Open(n) |
| 安全な公開 | Flag, 隣接数n | Flag |
| 安全な公開 | Open(m), 隣接数n | Open(m) |

「安全な公開」は地雷でないと盤面エンジンが確認した後の操作です。
地雷を踏む場合の状態遷移は別の要件として後から定めます。

## 1. LAWS.bendで先に宣言する

```bend
import Base
import ./game.bend as Game

law hidden_is_flagged:
  {Game.toggle_flag(Game.Hidden{}) == Game.Flag{} : Game.Square}

law opened_ignores_flag:
  for clue: U32
  {Game.toggle_flag(Game.Open{clue}) == Game.Open{clue} : Game.Square}

law flag_toggle_involution:
  for s: Game.Square
  {Game.toggle_flag(Game.toggle_flag(s)) == s : Game.Square}
```

最後の法則だけでは仕様が弱すぎます。何もしない関数も二回続ければ
元へ戻るためです。従ってHidden→FlagとFlag→Hiddenを別々の法則で
指定します。完全な7件の法則は [LAWS.bend](LAWS.bend) を参照してください。

## 2. 実装する

[game.bend](game.bend) では、`Square` を `Hidden`、
`Flag`、`Open{clue}` として定義します。
`toggle_flag` と `reveal_safe` は、副作用のない純粋関数です。

まず `reveal_safe(Open{2}, 4)` を頭の中で計算してみましょう。
新しい値で上書きするのではなく、元の `Open{2}` が残るはずです。

## 3. PROOF.bendで証明する

```bend
import Base
import ./game.bend as Game
import ./LAWS.bend as Laws

def Laws.flag_toggle_involution(s):
  match s:
    case Game.Hidden{}:
      {==}
    case Game.Flag{}:
      {==}
    case Game.Open{clue}:
      {==}
```

`match` の三分岐は、取り得るマスの状態すべてを網羅します。
`{==}` は具体例一つのテストではなく、その分岐の等式が
計算で一致することを確かめる証明です。

```sh
bend intermediate/minesweeper/game.bend
bend intermediate/minesweeper/PROOF.bend --verdict
```

`--verdict` の `ALL PROOFS CHECK` を確認します。
CIでも独立して同じ検査を行います。もしHiddenに旗を付ける
コードを何もしない処理へ変えると、二重切替の性質は保たれても
`hidden_is_flagged` に違反して証明は通りません。

## 4. 今回は何を保証したか

7件の法則が保証するのは**1マスの可視状態**です。
地雷数の算出、周囲のマス、地雷配置の保持、0の連鎖公開、
勝敗や初手安全、GUIについてはまだ保証していません。

次節から盤面を表すデータ型と、近傍が盤面外に回り込まないという
B-01の仕様へ進みます。

**演習**：`reveal_safe(Open{1}, 3)` は何を返すでしょうか。
結果を予想してから新しい確認用コードを書き、
その振る舞いを表す法則も追加してみましょう。


## 5. 盤面の端を越えないことを先に要求する（B-01）

ここからは一つのマスだけでなく、盤面のどこにマスがあるかを考えます。
前巻のライフゲームは端が反対側へ回り込むトーラスでしたが、
マインスイーパーでは左上の (0,0) と右下の (3,3) は隣接しません。

「端の扱い」を実装者の勘で決めるのではなく、先に法則にします。

```bend
import ./board.bend as Board

law board_no_wrap:
  {Board.neighbor(0, 0, 3, 3) == False{} : Bool}

law board_outside_x:
  for y: U32
  {Board.in_bounds(4, y) == False{} : Bool}
```

二つ目は y の値に関係なく、4列目（0起点）は幅4の盤面外であると
主張します。特定の座標を試すだけの場合と、任意の入力について法則を
証明する場合を意識して読み比べましょう。

[board.bend](board.bend) の `neighbor` は、両端の座標を
`in_bounds` で確認してから、横差・縦差がそれぞれ1以下か、
かつ同一セルでないかを調べます。`U32` は符号なし整数なので、
座標を検証する前に `x-1` を無条件に使うと、
0の前が反対側へ見えるような誤りを招き得ます。

この実装を、4×4の各16マスから他の16マスへの**256通りの組合せ**
すべてで、独立したPythonのオラクルと比較します。
数個の `law` が通るだけでは拾えない実装バグを検出するためです。

## 6. 内部の正解と公開情報を分ける（B-02/B-03）

[board.bend](board.bend) には内部専用の
`Cell{mine, square}` 型を定義しました。地雷の真偽値と
画面に見える `Square` を、同じ内部レコードに格納します。
ただしソルバーへ渡せる型ではありません。ソルバーは後で
地雷の正解を含まない `View` 型を受け取るよう設計します。

旗の操作でも、安全なマスの公開でも、地雷の真偽値を変更する
必要はありません。そこで次のように宣言します。

```bend
law board_toggle_keeps_mine:
  for mine: Bool
  for s: Game.Square
  {Board.mine_of(Board.toggle(Board.Cell{mine, s})) == mine : Bool}
```

これは地雷がある場合とない場合、さらにマスの可視状態がどれであっても、
旗の切替で地雷配置の真偽値が変化しないという約束です。
`PROOF.bend` では `Square` を場合分けして証明します。

この時点では、まだ盤面全体を表す `Array` の不変条件には
進んでいません。次節で扱います。`Board.reveal` も、呼び出し側が地雷でないことを
確認して使う低水準操作です。地雷を踏んだ際の敗北処理は、
先にG系列の法則として仕様化してから作ります。

**演習**：4×4盤面の (0,0)、(1,1)、(3,3) に
隣接するマス数をそれぞれ予想し、`neighbor` で確認してみましょう。
さらに、初めから公開済みのマスを公開し直しても
数字が変わらない理由を、対応する法則から説明してみましょう。


## 7. 16マスをひとまとまりで扱う（B-02）

これまで地雷があるかどうかは、1マスごとの `Bool` でした。
盤面全体になると、場所ごとの真偽値と、画面に表示する状態を
格納する必要があります。実装の前に、**盤面を操作しても地雷配置は
絶対に変えない**と決めます。

`board4.bend` では内部状態を次の二つに分けます。

- `mines: U32`：16マスに対応する地雷の16ビット。ビット `4*y+x`
  が1なら、そのマスに地雷があります。
- `cells: Array<Game.Square>`：各マスの `Hidden`、`Flag`、
  `Open{clue}` を格納する16要素の配列です。

盤面の初期化に使う `Array.new(Game.Square, 4n, ...)` は
`2^4=16` 個の要素を作ります。`Array` 自体は `Type` に属するため、
これをフィールドに持つ `State` も `type State is Type` とします。

コードより先に、任意のビットマスクと任意の配列に対して
次の性質を要求します。

```bend
law board4_toggle_keeps_all_mines:
  for mines: U32
  for cells: Array<Game.Square>
  for index: U32
  {Board4.mine_mask(Board4.toggle_at(
      Board4.State{mines, cells}, index)) == mines : U32}
```

この法則が主張しているのは、一つのマスの旗を切り替えても
**盤面内の地雷ビット列全体が同一**であることです。安全な公開についても
同様の法則を定義します。これで地雷の値を変更する実装は受け入れられません。
ただし、操作によってどのマスが変わるか、勝敗判定が正しいかは別の性質です。

## 8. 数字の意味を法則と独立したテストで確かめる（B-04）

(0,0) にだけ地雷がある盤面では、(0,0) 自身の周辺地雷数は0、
斜め隣の (1,1) は1です。さらに (1,1) に地雷を追加すると、
(1,0) の周辺地雷数は2になります。この例を
`clue` の実装前に `law` にします。

```bend
law board4_own_mine_not_counted:
  {Board4.clue(1, 0, 0) == 0 : U32}

law board4_diagonal_clue:
  {Board4.clue(1, 1, 1) == 1 : U32}

law board4_two_mines_clue:
  {Board4.clue(33, 1, 0) == 2 : U32}
```

`33=1+32` は、セル番号0と5に地雷があることを意味します。
一般のビットマスクでも正しいかを確かめるため、
6種類の配置×16マス、16種類の単独地雷配置、
マス操作と範囲外操作を合わせた**154件**の実行テストを用意しました。
期待値はPythonで各地雷と隣接座標の関係から独立に計算しています。

`law` の証明と実行テストを両方使うのは、両者が保証する対象が
異なるためです。地雷ゼロならどの座標でも `clue` が0になるという
**全称法則**は形式的に証明しましたが、一般の地雷配置について
常に正しいことは、現時点で全称証明していません。

## 9. 配列外のクリックを拒否する（B-05）

配列の添字に16を渡したとき、プログラムが自動的に
「範囲外」と判定してくれると考えるのは危険です。
Bendの `Array.get` は内部で添字を折り返す挙動があるためです。

そこで `toggle_checked` と `reveal_checked` は最初に
`index < 16` を調べ、範囲外なら元の状態を返すようにします。
この要求もコードの前に `law` として書きました。
型が正しいだけでは、この規則は自動的に保証されません。

現段階の`reveal_checked`も、**呼び出し側が安全と判定して
正しい数字を渡す**低水準操作です。最初のクリックの安全、
地雷を踏んだ場合の敗北、数字を自動計算して公開する一連の処理は
次節で段階的に設計します。

**演習**：4×4盤面のマス(1,1)は何番の添字になるでしょうか。
また、添字16のクリックを拒否しない実装では、どのマスが
誤って操作され得るか考え、境界検査付きの関数を動かしてみましょう。


## 10. クリックから勝敗までを組み立てる（G-02/G-03）

以前の `reveal_checked` は、安全なマスを開くための**数字を引数として受け取る**
低水準操作でした。しかし、マウスから渡されるのはクリックした位置であり、
数字ではありません。地雷の有無を調べ、数字を計算する操作を追加します。

まず実装を読む前に、地雷をクリックすると `Lost` になると決めます。

```bend
law session_mine_click_loses:
  {Session.phase_of(Session.click(Session.new(1), 0))
      == Session.Lost{} : Session.Phase}
```

地雷マスク `1` は左上のマスだけが地雷であることを意味します。
この法則だけでは旗の保護までは保証できないので、旗を付けてからクリックした
場合は `Playing` のままという別の法則も用意します。

### 勝利には旗でなく公開が必要です

地雷と同じ数だけ旗を置いたとしても、安全なマスが隠れたままなら
勝利ではありません。**安全なマスがすべて `Open` になったときだけ**
勝利します。これが [session.bend](session.bend) の判定です。

確認するためには16要素の `Array` を調べる必要がありますが、
調べた後もゲームの盤面は保持しなければなりません。そこで
**Bendの標準API `Array.clone`** で盤面を複製し、
検査用の配列だけを **`Array.to_list`** で `List` に変換します。
このように、用意された関数が処理に合うなら積極的に使用します。

検査自体は `List` の短い再帰にしてあります。
状況によっては高階関数の `List.all` や `List.fold` を使う方が自然ですが、
不要な中間データや変換が増えるなら単純な再帰の方が適切です。
本書の目的は高階関数を避けることではなく、
**標準の機能を理解して適切な手段を選べるようになること**です。

### どこまで保証できたでしょうか

`session.bend` には `Playing`、`Won`、`Lost` の三つの状態があり、
終了後のクリックと旗操作は無視します。純粋なゲーム進行について
新しい7件の法則を `--verdict` で検査し、
独立した86ケースの実行テストで複数クリックや地雷の表示を照合しました。

ただし、一般の地雷配置すべてに対する勝利条件の必要十分性は
まだ全称証明していません。**初手安全と0マスの連鎖公開も未実装**です。

**演習**：地雷マスク `65534` の盤面では、どのマスだけが安全でしょうか。
そこを一度開いたら `Won` になることと、先に旗を立てていたら開けないことを
`session.bend` を読んで説明してみましょう。

## 11. 初手安全を配置済みセッションと分離する（G-01）

初手で地雷を踏まない規則と、既に地雷が確定した通常のクリックで地雷を踏めば
敗北する規則は、違う局面の話です。後者の `session_mine_click_loses` を消して
「安全」と呼ぶのは仕様の弱体化です。

そこで `start.bend` に、プレイヤーがまだ一度も左クリックしていない
`Fresh` と、配置が確定した `Active` を分けました。初めてクリックした場所が
地雷なら、空いている最小添字へ地雷を1個移動させます。
移動しても地雷の個数は変えません。地雷のない位置をクリックしたなら動かしません。

```bend
law start_relocates_clicked_mine:
  {Start.mine_mask(Start.click(Start.new(1), 0)) == 2 : U32}

law start_first_square_opened:
  {Start.visible_at(Start.click(Start.new(1), 0), 0) == Game.Open{1} : Game.Square}
```

地雷16個は移動先がないため開始拒否、添字16の初手も範囲外として無視します。
この6法則は独立して宣言した後で実装・証明し、既存の31法則と合わせて
`--verdict` で37法則を検査しました。別のPython計算から178ケースの
初手配置・可視数字・開始前状態も照合しました。これはすべての盤面の
一般全称証明やGUI操作検証と同じではありません。

**演習**：地雷が (0,0) と (1,1) の二つ（マスク33）の盤面で、
最初に(0,0)を開くとどのビットが移動するか予想してください。
最も番号の小さい空きマスへ移す規則では、移動後のマスクは34です。
次に、最初に安全な(3,3)をクリックしたら移動が必要か考えてみましょう。
